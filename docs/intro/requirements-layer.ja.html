要件層 requirements は、要件ID、入力、条件、受け入れ手順、禁止手順、非機能要件を書く層です。業務意図を、テストと設計へ渡せる粒度まで具体化します。

読み方の前提: requirements、process、acceptance などはFSLの予約語です。本文では「要件層」「工程」「受け入れ手順」のように日本語名を併記します。

1. 役割

要件層は、業務意図を入力・条件・例に分解する

業務層が「何を業務として守るか」を書くのに対し、要件層は「どの入力で、どの条件なら、どう進むか」を書きます。

業務層

申請は判断される、承認後だけ支払う、返金は完了状態にできる。業務担当者が確認する抽象度。

要件層

金額入力、しきい値、自動承認、管理者承認、受け入れ手順、拒否されるべき手順。企画・受け入れ確認の抽象度。

重要: 要件層では、要件IDと原文を落とさないことが最優先です。反例が出たとき、どの要求が破れたのかをJSONから辿れるようにします。

2. 基本形

process に入力・条件・更新・要件IDを足す

単一の業務対象がステージを進む要件は、process Entity with field: Type で書くのが基本です。

版（edition）: process / transition の形と、このページのほかの例は FSL 4 です。ヘッダーのない文書（または fsl 4 で始まる文書）がこの構文で読まれます。fsl 5 で始まる文書では、要件仕様の process は拒否され（mixed_requirements_forms、終了コード 2）、要件は entity / lifecycle / event / rule / decide で書きます。書き方は 2b にあります。詳しくは FSL 5 の要件層リファレンス と FSL 4 から FSL 5 への移行ガイド を参照してください。

FSL 4（ヘッダーなし）

requirements ExpenseRequirements {
  number Amount
  const AUTO_LIMIT = 1

  process Claim with amount: Amount {
    stages Draft, Submitted, Approved, Rejected, Paid
    initial Draft
    transition submit Draft -> Submitted by Employee
      with a: Amount
      when a > 0
      set amount = a
      covers REQ-EXPENSE-001 "申請者が金額を入力して経費を申請する"

    transition auto_approve Submitted -> Approved by System
      when amount <= AUTO_LIMIT
      covers REQ-EXPENSE-002 "少額申請は自動承認される"

    transition mgr_approve Submitted -> Approved by Manager
      when amount > AUTO_LIMIT
      covers REQ-EXPENSE-003 "高額申請は管理者が承認する"

    transition reject Submitted -> Rejected by Manager
      when amount > AUTO_LIMIT
      covers REQ-EXPENSE-003 "高額申請は管理者が却下できる"

    transition pay Approved -> Paid by Finance
      covers REQ-EXPENSE-004 "承認済み申請だけが支払われる"
  }
}

verify {
  instances Claim = 3
  values Amount = 0..3
}
構文意味書くときの目安
number Amount数値の種類。範囲は verify { values ... } で指定します。
process Claim with amount: Amountステージと持ち回るデータ。申請金額、期限、区分など、要件判断に必要な値。
with a: Amount操作の入力。ユーザーやシステムが操作時に渡す値。
when ...実行できる条件。しきい値、状態、権限、期限など。
set amount = a持ち回るデータの更新。あとで判断に使う値だけ保存します。
covers REQ-EXPENSE-001 "..."要件IDと原文。診断JSON、反例、シナリオに伝わります。

2b. 同じ要件を FSL 5 で書く

fsl 5 ヘッダーのもとでは、entity がフィールドと lifecycle の辺を持ち、event は担当者が辺を一つ進める操作です。条件は rule か decide 表に、要件IDと原文つきで書きます。scenario / forbidden が正例と負例の手順です。この仕様は check を通り、深さ 8 で verified、--engine induction で proved になります。

FSL 5

fsl 5
requirements ExpenseRequirements {
  number Amount
  const AUTO_LIMIT = 1
  actor Employee, System, Manager, Finance

  entity Claim {
    amount: Amount = 0
    lifecycle Draft -> Submitted -> Approved
    lifecycle Submitted -> Rejected
    lifecycle Approved -> Paid
  }

  concept SmallClaim = Claim where amount <= AUTO_LIMIT
  concept LargeClaim = Claim where amount > AUTO_LIMIT

  event submit       = Employee submits Claim with amount  Draft -> Submitted
  event auto_approve = System approves Claim               Submitted -> Approved
  event mgr_approve  = Manager approves Claim              Submitted -> Approved
  event reject       = Manager rejects Claim               Submitted -> Rejected
  event pay          = Finance pays Claim                  Approved -> Paid
    covers REQ-EXPENSE-005 "承認済み申請だけが支払われる"

  rule REQ-EXPENSE-001 "申請者が金額を入力して経費を申請する" {
    allow Employee submits Claim only when input amount > 0
  }

  decide REQ-EXPENSE-002 "申請を誰が判断するか" for Submitted Claim {
    SmallClaim => System approves
      covers REQ-EXPENSE-003 "少額申請は自動承認される"
    LargeClaim => Manager approves or rejects
      covers REQ-EXPENSE-004 "高額申請は管理者が承認または却下する"
  }

  scenario AC-EXPENSE-001 "少額申請は支払いまで進める" {
    Employee submits c1 with amount 1
    System approves c1
    Finance pays c1
    then c1 is Paid
  }
  forbidden FB-EXPENSE-001 "金額0では申請できない" {
    Employee submits c1 with amount 0
    then rejected
  }
  forbidden FB-EXPENSE-002 "下書き申請は支払えない" {
    Finance pays c1
    then rejected
  }
}
verify {
  instances Claim = 3
  values Amount = 0..3
}
FSL 4FSL 5
process Claim with amount: Amount { stages … initial … }entity Claim { amount: Amount = 0 lifecycle Draft -> Submitted … }。最初のステージが初期ステージです。
transition submit Draft -> Submitted by Employee with a: Amount … set amount = aevent submit = Employee submits Claim with amount Draft -> Submitted。入力はフィールドに保存されます。
when a > 0 と covers REQ-…rule REQ-… "…" { allow Employee submits Claim only when input amount > 0 }
しきい値ごとに遷移へ書く whendecide 表。場合ごとに 1 行、それぞれに covers。
acceptance … expect Claim 0 in Paidscenario … then c1 is Paid。番号の代わりにインスタンスのラベルを使います。
forbidden … expect rejectedforbidden … then rejected

FSL 4 のファイルは fslc migrate --edition 5 file.fsl で変換案を確認できます。書き込む前に 移行ガイド を読んでください。

3. 受け入れ・禁止

許す手順は acceptance、拒否すべき手順は forbidden

安全ルールだけでは「本来拒否されるべき操作が受け入れられた」ことを見逃す場合があります。要件層では、正例と負例を両方書きます。下の手順は FSL 4 の形です。FSL 5 の形は 2b にあります。

受け入れ手順

acceptance AC-EXPENSE-001 "少額申請は支払いまで進める" {
  submit(0, 1)
  auto_approve(0)
  pay(0)
  expect Claim 0 in Paid
}

許可されるべき手順です。検査時に実行され、シナリオやテスト生成にも流れます。

禁止手順

forbidden FB-EXPENSE-001 "下書き申請は支払えない" {
  pay(0)
  expect rejected
}

最後の操作が拒否されるべき手順です。受け入れられた場合、条件が弱すぎることがわかります。

使い分け: acceptance は「できるべきこと」を守ります。forbidden は「できてはいけないこと」を守ります。重要な要件には、できる例と拒否される例をペアで置くと読みやすくなります。

4. 非機能要件

権限・監査・容量・期限は、要件層で扱う

非機能要件の多くは、通常の条件や安全ルールで書けます。期限のように時間を扱うものだけ、time と deadline を使います。下の SLA の基本形は FSL 4 の形です。

非機能要件書き方注意
権限操作条件 when または requires。誰が実行できるかを曖昧にしない。
監査監査状態と安全ルール。イベントログが必要なら設計層・実装接続へ送る。
容量範囲つき数値、列 Seq の容量、件数の上限。境界は手書きルールではなく型で表せるなら型に寄せる。
SLA・期限time + deadline。実時間ミリ秒ではなく、離散的な tick として検査する。
確率・百分位・使いやすさFSL外の文書に書く。FSLで直接保証しません。

SLA の基本形

requirements SupportSLA {
  entity Ticket
  const SLA_TICKS = 3
  enum TicketStage { New, Accepted, Responded }

  state { tickets: Map<Ticket, TicketStage> }
  init {
    forall t: Ticket { tickets[t] = New }
  }

  time {
    urgent respond_due
    age wait_age[t: Ticket] while tickets[t] == Accepted
  }

  requirement NFR-1 "受理から3 tick以内に応答する" {
    action accept(t: Ticket) {
      requires tickets[t] == New
      tickets[t] = Accepted
    }

    fair action respond_due(t: Ticket) {
      requires tickets[t] == Accepted
      requires wait_age[t] >= SLA_TICKS
      tickets[t] = Responded
    }

    deadline wait_age <= SLA_TICKS
  }
}

verify {
  instances Ticket = 2
}

SLAの落とし穴: いつでも有効な操作を urgent にすると、時間が進まず、期限が空虚に通ることがあります。期限到達時にだけ有効になる操作を urgent にします。

5. 業務層との接続

implements で、要件が業務意図を落としていないか見る

要件層が業務層を実装する場合、implements Abs from "file" { } を置きます。名前がそろっていれば、FSL が対応表を自動生成できます。

FSL 5 の要件仕様も同じ行で始めます。ただし入力を取るイベントは業務層の遷移より引数が多いため、action submit(c, amount) -> submit(c) のような対応を明示します。また、ステージが lifecycle の行に初めて現れる順序を、業務層の工程と同じにします。両方のファイルは 業務層の受け渡し にあります。

名前一致でつなぐ

requirements ExpenseRequirements {
  implements ExpenseToBe from "business.fsl" { }
  ...
}

業務層と同じ対象名・ステージ名・遷移名を使うと、自動対応しやすくなります。

ずれがある場合

implements ExpenseToBe from "business.fsl" {
  maps auto
  map status = req_status
}

名前や構造が違う場合は、明示的な対応を書きます。

検証時の見え方

$ fslc verify requirements.fsl --depth 8
# seam が失敗すると top-level result になり exit 1
# implements.result は "refines" だけが合格値

要件自身の検証に加えて、業務層への詳細化結果が implements に含まれます。

seam の終了コード: 壊れた implements リンクは入れ子のフィールドの中に閉じません。refinement_failed と impl_violated は top-level の result になり、violated と同じくコマンドは exit 1 で終了します。残る穴が1つあります: --property、--exclude-property、--from-state でスコープした verify は implements 自体を省略するため、seam をゲートできません(#1008)。スコープ無しの check/verify、または fslc chain でゲートしてください — 全体の流れは e2e 連鎖 を参照。

6. チェックリスト

要件層レビューで見ること

  1. 各遷移に要件IDがあるか

    covers REQ-... がないと、反例から原要求へ戻りにくくなります。

  2. 境界値が明示されているか

    <= AUTO_LIMIT と > AUTO_LIMIT のように、境界を曖昧にしません。

  3. 受け入れ手順と禁止手順が両方あるか

    正例だけだと条件の弱さを見逃します。重要な拒否条件には forbidden を置きます。

  4. 非機能要件をFSLで書けるものと書けないものに分けたか

    権限・監査・容量・SLAは書けます。確率、百分位、実時間ミリ秒、使いやすさは文書に残します。

  5. 業務層を弱めていないか

    implements の失敗は、要件が業務意図を落とした可能性として読みます。
