The requirements layer carries requirement IDs, inputs, guards, acceptance flows, forbidden flows, and NFRs. It makes business intent concrete enough for design and tests.

1. Boundary

Requirements split business intent into inputs, guards, and examples

The business layer says what the organization allows. The requirements layer says which inputs and conditions move the lifecycle, and which concrete flows must be accepted or rejected.

Business layer

A claim is eventually decided; only approved claims are paid; refund handling can reach a settled state.

Requirements layer

Amount input, thresholds, auto approval, manager approval, acceptance flows, forbidden flows, and NFRs.

Priority: preserve requirement IDs and original text. Counterexamples should tell reviewers which request broke.

2. Basic Shape

Add inputs, guards, updates, and traceability to process

For a single-entity lifecycle, start with process Entity with field: Type.

Edition: the process / transition form and the other examples on this page are FSL 4: a document with no header (or with fsl 4) is read with this syntax. A document headed fsl 5 refuses a process in a requirements spec (mixed_requirements_forms, exit 2) and writes requirements with entity / lifecycle / event / rule / decide, shown in 2b. See the FSL 5 requirements reference and the FSL 4 to FSL 5 migration guide.

FSL 4 (headerless)

requirements ExpenseRequirements {
  number Amount
  const AUTO_LIMIT = 1

  process Claim with amount: Amount {
    stages Draft, Submitted, Approved, Rejected, Paid
    initial Draft
    transition submit Draft -> Submitted by Employee
      with a: Amount
      when a > 0
      set amount = a
      covers REQ-EXPENSE-001 "The applicant submits an expense claim by entering an amount"

    transition auto_approve Submitted -> Approved by System
      when amount <= AUTO_LIMIT
      covers REQ-EXPENSE-002 "Claims at or below AUTO_LIMIT are auto-approved"

    transition mgr_approve Submitted -> Approved by Manager
      when amount > AUTO_LIMIT
      covers REQ-EXPENSE-003 "Claims above AUTO_LIMIT are approved by a manager"

    transition reject Submitted -> Rejected by Manager
      when amount > AUTO_LIMIT
      covers REQ-EXPENSE-003 "Claims above AUTO_LIMIT may be rejected by a manager"

    transition pay Approved -> Paid by Finance
      covers REQ-EXPENSE-004 "Only approved claims are paid"
  }
}

verify {
  instances Claim = 3
  values Amount = 0..3
}

2b. The same requirements in FSL 5

Under the fsl 5 header, an entity holds the fields and the lifecycle edges, an event is one actor's move along an edge, a rule or a decide table states the condition with the requirement ID and its source text, and scenario / forbidden are the positive and negative traces. This specification checks, verifies to depth 8, and proves with --engine induction.

FSL 5

fsl 5
requirements ExpenseRequirements {
  number Amount
  const AUTO_LIMIT = 1
  actor Employee, System, Manager, Finance

  entity Claim {
    amount: Amount = 0
    lifecycle Draft -> Submitted -> Approved
    lifecycle Submitted -> Rejected
    lifecycle Approved -> Paid
  }

  concept SmallClaim = Claim where amount <= AUTO_LIMIT
  concept LargeClaim = Claim where amount > AUTO_LIMIT

  event submit       = Employee submits Claim with amount  Draft -> Submitted
  event auto_approve = System approves Claim               Submitted -> Approved
  event mgr_approve  = Manager approves Claim              Submitted -> Approved
  event reject       = Manager rejects Claim               Submitted -> Rejected
  event pay          = Finance pays Claim                  Approved -> Paid
    covers REQ-EXPENSE-005 "Only approved claims are paid"

  rule REQ-EXPENSE-001 "The applicant submits an expense claim by entering an amount" {
    allow Employee submits Claim only when input amount > 0
  }

  decide REQ-EXPENSE-002 "Who decides a submitted claim" for Submitted Claim {
    SmallClaim => System approves
      covers REQ-EXPENSE-003 "Claims at or below AUTO_LIMIT are auto-approved"
    LargeClaim => Manager approves or rejects
      covers REQ-EXPENSE-004 "Claims above AUTO_LIMIT are approved or rejected by a manager"
  }

  scenario AC-EXPENSE-001 "A low-amount claim can be paid" {
    Employee submits c1 with amount 1
    System approves c1
    Finance pays c1
    then c1 is Paid
  }
  forbidden FB-EXPENSE-001 "A claim of zero cannot be submitted" {
    Employee submits c1 with amount 0
    then rejected
  }
  forbidden FB-EXPENSE-002 "A draft claim cannot be paid" {
    Finance pays c1
    then rejected
  }
}
verify {
  instances Claim = 3
  values Amount = 0..3
}

3. Positive and Negative Examples

Use acceptance for must-allow and forbidden for must-reject

A safety invariant can miss under-constraint. Requirements should include both flows that must work and flows that must be rejected. The traces below are FSL 4; 2b shows their FSL 5 form.

Acceptance flow

acceptance AC-EXPENSE-001 "low-amount claims can be paid" {
  submit(0, 1)
  auto_approve(0)
  pay(0)
  expect Claim 0 in Paid
}

A flow that must be accepted. It is replay-checked and flows into scenarios and test generation.

Forbidden flow

forbidden FB-EXPENSE-001 "draft claims cannot be paid" {
  pay(0)
  expect rejected
}

A flow whose final step must be rejected. If it is accepted, a guard is probably too weak.

4. Non-Functional Requirements

Permission, audit, capacity, and deadlines can be modeled here

Many NFRs become ordinary guards or invariants. Deadlines use time and deadline. The SLA pattern below is FSL 4.

NFRHow to write itNote
Permissionwhen or requires role checks.Make who can run the operation explicit.
AuditAudit state plus safety rules.Implementation logs connect later through replay.
CapacityBounded numeric types, Seq capacity, count bounds.Prefer type bounds where possible.
SLA / timeouttime + deadline.Discrete ticks, not wall-clock milliseconds.
Probability, percentiles, usabilityKeep in prose documents.FSL does not directly guarantee them.

SLA pattern

time {
  urgent respond_due
  age wait_age[t: Ticket] while tickets[t] == Accepted
}

requirement NFR-1 "respond within 3 ticks after acceptance" {
  fair action respond_due(t: Ticket) {
    requires tickets[t] == Accepted
    requires wait_age[t] >= SLA_TICKS
    tickets[t] = Responded
  }

  deadline wait_age <= SLA_TICKS
}

SLA trap: if an always-enabled action is urgent, time can freeze and the deadline may pass vacuously. Make only the deadline-reached handler urgent.

5. Business Connection

implements checks that requirements preserve business intent

When requirements implement a business spec, add implements Abs from "file" { }. If names match, FSL can synthesize the mapping.

The same line opens an FSL 5 requirements spec. There, an event that takes an input has more parameters than the business transition, so it needs an explicit correspondence such as action submit(c, amount) -> submit(c), and the stages must first appear in the lifecycle lines in the business process's order. The business-layer handoff shows both files.

Name-aligned connection

requirements ExpenseRequirements {
  implements ExpenseToBe from "business.fsl" { }
  ...
}

Keep entity, stage, and transition names aligned when the meaning is the same.

Explicit mapping

implements ExpenseToBe from "business.fsl" {
  maps auto
  map status = req_status
}

Use explicit maps only when names or structure differ.

Verification

$ fslc verify requirements.fsl --depth 8
# a failed seam becomes the top-level result and exits 1
# "refines" is the only passing implements.result

The JSON includes both requirements verification and the business refinement result under implements.

Seam exit code: a broken implements link is not confined to the nested field. refinement_failed and impl_violated become the top-level result and the command exits 1, the same class as violated. One gap remains: a verify scoped with --property, --exclude-property, or --from-state omits implements altogether and therefore cannot gate the seam (#1008). Gate on an unscoped check/verify, or on fslc chain — see the e2e chain for a full walkthrough.

6. Checklist

Review before design

  1. Does every important transition carry a requirement ID?

    Without covers REQ-..., counterexamples are harder to trace back to source intent.

  2. Are boundary conditions explicit?

    Spell out <= AUTO_LIMIT versus > AUTO_LIMIT. Boundary mistakes are common.

  3. Do you have both acceptance and forbidden flows?

    Positive examples alone can miss weak guards.

  4. Did you separate FSL-checkable NFRs from prose-only NFRs?

    Permission, audit, capacity, and SLA can be modeled. Probability, percentiles, real milliseconds, and usability stay in prose.

  5. Did the layer weaken business intent?

    Treat an implements failure as a possible loss of business meaning.

Next: hand off to design

Once requirements are stable, use spec and refinement mappings for implementation-near state and actions.
