# Soundness-critical semantic mutation gate

Status: accepted. Implemented by issue #672.

## Decision

FSL calibrates the detection power of tests over soundness-critical native Rust
code with two complementary mutation families:

1. reviewed semantic fault operators in
   `rust/fslc/tests/fault_operators/operators.txt`; and
2. generic source mutations generated by exactly `cargo-mutants 27.1.0` over
   the maintained scope in
   `rust/fslc/tests/implementation_mutation/scope.v1.json`.

The first pilot is P2 symbolic-witness/concrete-replay agreement. Mutation
testing is a detector calibration method. It is not another observer, never
promotes a public assurance class, and never changes a product process exit.
Specification mutation through `fslc mutate` remains a separate user-facing
domain. (`fslc mutate`'s own `domain`-dialect acceptance normative text — issue
#727 — lives in `docs/DESIGN-mutate.md` §2, not here, per that document's scope
above.)

## Scope and anchors

The scope manifest is the authority for generic mutation. Every entry names a
repository-relative Rust file, a stable decision ID, the containing function,
an exact source anchor, and the false-green classes at risk. The manifest test
requires every anchor to occur exactly once. A moved or ambiguous anchor fails
before mutation starts. Files and decisions outside the pilot are listed with
reasons; no repository-wide percentage is reported.

Every generic function must map to at least one maintained decision. At report
time the runner derives each decision's current line from its exact anchor and
maps a mutant back to the nearest containing decision region. A bare function
name is never emitted as a substitute for decision traceability.

Line-scoped generic exclusions are allowed only for a uniquely anchored
decision that is explicitly outside the pilot. An exclusion records its
selected `occurrence` and the anchor's `expected_occurrences` total; generation
refuses any source whose actual total differs, so a comment or code duplicate
cannot silently rebind a positional occurrence. The generator derives the
cargo-mutants line expression from that checked anchor into
`rust/.cargo/mutants.toml`; its freshness check reports the first differing
generated line and the regeneration command, so source movement cannot leave a
hand-copied line exclusion behind. Such exclusions are scope declarations, not
equivalent mutants.

The P2 pilot covers:

- SAT/UNSAT/unknown and backend-error classification in bounded verification;
- inclusive depth and step handling;
- symbolic witness state/action projection;
- violation kind/name and property-location projection;
- solver-independent replay acceptance; and
- failure/inconclusive result folding.

## Reviewed semantic operators

`operators.txt` is the single operator inventory. Each row declares the
violated contract, exact source anchor, patch, primary detector, blind detector,
expected verdict change, calibrated P2 edge, and source scope. The runner
requires the primary to fail and the blind detector to remain green. It also
runs the no-op control and requires the stale-seam control to be refused.
Action omission, replay bypass, violation-kind substitution, and
violation-name substitution are separate operators and controls; a combined
fault cannot stand in for independent detection of those witness fields.

A patch that does not apply is a harness failure. A compile failure is not a
kill for a reviewed semantic operator: the operator was designed to be
compilable, so an unbuildable result means its seam or mutation is stale.

## Generic runner and classifications

The native Rust mutation runner is pinned to `cargo-mutants 27.1.0` in CI and
checked at runtime before use. Its durable output (`mutants.json`,
`outcomes.json`, per-mutant diff and log files, plus caught/missed/timeout/
unviable lists) is retained as the raw observation. The FSL gate maps outcomes
as follows:

| cargo-mutants outcome | FSL classification | Gate effect |
|---|---|---|
| caught | `killed` | pass |
| missed | `survived` | fail unless a valid reviewed-equivalent entry matches |
| timeout | `timeout` | fail; incomplete evidence |
| unviable | `unbuildable` | recorded, not a semantic kill |
| missed + accepted exact equivalence | `reviewed_equivalent` | pass only while its anchor and rationale remain valid |

Any runner summary outside these four native cargo-mutants outcomes fails
before report generation. Timeout gating is computed from authoritative
`outcomes.json` and cross-checked against `timeout.txt`; an empty or missing
side list cannot turn a timeout green.

Reviewed equivalence is maintained in
`rust/fslc/tests/implementation_mutation/equivalents.v1.json`. Every entry must
name an exact stable mutant ID, one unique source anchor, a non-empty semantic
rationale, reviewer, and review issue. Glob or line-range exclusions are
forbidden. The manifest validator has rejecting controls for missing rationale,
stale anchors, and ambiguous anchors. On a complete run every reviewed mutant
ID must still occur in the current raw outcome inventory; an anchor that
survives while its exact mutant disappears is also stale and fails closed.

The repository contains Rust integration fixtures that use `include_str!` on
top-level `examples/`. Cargo-mutants otherwise copies only the nested Rust
workspace and produces an unfaithful baseline with those files absent. The FSL
runner therefore copies the full repository (excluding build/VCS/dependency
artifacts) to an isolated checkout, initializes its repository boundary, and
uses cargo-mutants' in-place mode only inside that disposable checkout. This
preserves full-repository fixture semantics without ever mutating the caller's
working tree.

Each invocation also receives a fresh Cargo target. Reusing one target across
disposable checkouts is forbidden: after interruption, a compiled mutant can
be newer than a restored source file and contaminate the next unmutated
baseline. The fresh target keeps baseline evidence independent of prior runs.

## Tiered execution

- Pull requests run every curated P2 operator plus generic mutants touching the
  changed lines of the declared critical scope. The diff is captured against
  the PR base revision and passed to cargo-mutants with `--in-diff`.
- `main`, scheduled, manual, and promotion evidence run every curated operator
  plus the complete declared P2 generic scope.
- Every tier runs an unmutated baseline first. A zero-mutant changed-code run is
  valid only when the recorded diff contains no changed declared decision; the
  curated controls and the generic detector tests still run. Because
  cargo-mutants emits no raw directory for this case, the wrapper retains its
  empty filtered inventory and emits an explicit complete zero-mutant report.
  If cargo-mutants lists zero line mutants while the diff still touches an
  in-scope critical path, the runner escalates to the complete P2 generic scope
  instead of accepting an ambiguous zero.
- Timeout, absent output, malformed output, missed mutants, a stale operator,
  or a stale equivalence entry fails closed. Shards are complete only when all
  declared shards publish outcomes for the same revision and tool version.

### CI scheduling: two lanes, one aggregator

The curated operator half and the generic cargo-mutants half are wall-clock-independent by
construction, so CI runs them as separate jobs behind an aggregator that carries the required
`semantic mutation (...)` context (docs/DESIGN-ci.md, "Sharded pre-merge Linux evidence").
This is a scheduling change only: every check that ran before still runs, in the same
tier (`changed`/`complete`), with the same classifications and the same evidence contract.

- `semantic-mutation-operators` (3-way matrix) runs
  `tools/run-semantic-mutation-gate.sh <mode> --lane operators --shard K/3`. Each shard gets a
  round-robin third of `operators.txt` by 0-based row index (`operator i` belongs to shard `K` iff
  `i % 3 == K - 1`), assigned by `tools/run-fault-operators.sh`'s `assign_shard`. The whole-table
  validation in `read_table` (missing patch file, orphaned patch, malformed row) and the harness's
  own `check_stale_seam_control` negative control run in **every** shard, not just one — a fault in
  either must be caught regardless of which shard happens to run it. `check_no_op_control`'s loop and
  the main operator loop are both restricted to the shard's assigned indices, which is what makes the
  ~912s no-op control shardable at all.
- `semantic-mutation-mutants` runs `tools/run-semantic-mutation-gate.sh <mode> --lane mutants`,
  complete and **unsharded**: at the measured ~14.3 min it is already close to the curated lane's
  post-split floor, and cargo-mutants sharding (mutant-inventory slicing, uncertain
  `--shard`/partition index-base semantics in the pinned runner, migrating the stale-reviewed-
  equivalents check) would add real risk for no measured wall-clock gain.
- The `semantic-mutation` aggregator requires both lanes to report `success` (`if: always()`, so a
  failing shard cannot be masked by a GitHub-treated-as-satisfied *skip* of the aggregator), then
  downloads every stable-name operator shard artifact. The names omit `run_attempt`, so a partial
  rerun may validly aggregate compatible attempts such as `[N,N+1,N]`. Before content completeness,
  `tools/check-shard-artifact-cohort.sh semantic` requires exactly one provenance sidecar for each
  logical shard and validates its schema, lane/run/revision/shard identity, bounded attempt, and
  canonical payload checksums. It then enforces identical `base_revision` and raw JSON-array-exact
  `table_operators` across all three manifests (canonicalization is only for checksums and set-union
  input), and the disjoint union of their
  `executed_operators` equal to `table_operators` exactly (via `tools/check-shard-union.sh`, the same
  fail-closed subset/disjoint/union-equality primitive used by the `rust workspace` split). A shard
  writes its manifest and provenance only after it succeeds, so a failed shard cannot contribute
  evidence that reads as complete; its `if: always()` upload remains diagnostic only.

With no `--lane` flag, `tools/run-semantic-mutation-gate.sh`'s behavior is unchanged from before this
split: the same manifest test, the same unsharded `run-fault-operators.sh` call, and the same
cargo-mutants run, in the same order. This is the path `tools/check-native-integration.sh
semantic-mutation` and every local invocation still take. `--lane`/`--shard` are additive, CI-only
scheduling controls.

The product entrypoint for a complete, unsharded local run is
`tools/check-native-integration.sh semantic-mutation`. It does not invoke the frozen Python
reference.

## Survivor promotion

A non-equivalent survivor remains a failing gate until a minimized ordinary
Rust regression kills it. The regression records the stable mutant ID and the
violated contract in its test documentation. Reclassifying a survivor as
equivalent requires an exact manifest entry and independent review; another
green test surface is not a waiver.

## Evidence contract

Every run binds evidence to the base revision, diff scope, runner version and
configuration, stable mutant ID, maintained decision anchor, exact test
command, outcome, elapsed time, replay command, and the named primary failing
test for every killed mutant. Raw cargo-mutants
output is never rewritten into a more favorable classification. Random order
may improve throughput, but stable mutant IDs and the recorded revision must
make each case replayable.

## Non-goals

- repository-wide mutation percentages or 100% mutation score;
- treating mutation count as proof of verifier soundness;
- adding a fault-injection switch to the shipped verifier;
- replacing Triangulated Assurance, the C3 matrix, or `fslc mutate`;
- using the frozen Python implementation as product evidence.
